# Разбор ТЗ VK CaseChamp для Python-разработчика

Версия ТЗ 1.0.0 от 20 ноября 2026 года. «Собрать как в посте» — демонстрационный сервис покупки набора для сервировки. Продавец импортирует каталог, связывает контент с товарами и публикует шаблон. Покупатель получает точный комплект под свои условия, резервирует его и оформляет тестовый заказ. За Python-часть, подбор, складские транзакции, фоновые процессы и ML отвечает D2.

Рабочая папка проекта — `casechamp_dev/`. Распакованная спецификация находится в [VK_CaseChamp_TZ_v1](VK_CaseChamp_TZ_v1/README.md). Архив и его 59 распакованных файлов имеют статус untracked. Спецификация и рабочая реализация хранятся в разных каталогах.

## Python и взаимодействие с frontend

- Стек D2 — Python 3.12, uv, FastAPI, Pydantic 2, Uvicorn, SQLAlchemy 2, psycopg 3, Alembic, PostgreSQL 17, OR-Tools CP-SAT, pytest и Hypothesis. API и worker используют один Python-пакет. Для продукта предусмотрены собственные lock-файл, миграции и Compose. Lock из архива предназначен для проверки ТЗ.
- D1 ведёт React/TypeScript/Vite/VKUI и генерирует клиент из OpenAPI. Backend выдаёт `{data, meta}` либо `{error, meta}`. В `meta` передаются `request_id`, серверные UTC-часы, epoch и флаг replay. Денежные поля — целые копейки. Pydantic-валидации предшествует строгий разбор JSON с проверкой дублирующихся ключей, `NaN`, `Infinity` и malformed body.
- Bootstrap создаёт песочницу на 24 часа и выдаёт HttpOnly cookie. Мутации проверяют точный `Origin`. Идентичность магазина берётся из сессии, ссылки на ресурсы ограничены sandbox и epoch. Reset атомарно закрывает старую эпоху, снимает её активные резервы и создаёт seed новой. Вкладки разделяют cookie, `client_run_id` используется для трассировки.
- CSV импортируется через preview и атомарный commit. Существующие SKU сохраняют слот, размер упаковки, цвет и геометрию. Цена, название, сроки обработки и изображение версионируются. Изменение физического остатка имеет отдельную inventory version. Снятие товара с продажи выполняет отдельная команда withdrawal.
- Продавец подтверждает primary для всех шести слотов, включая два необязательных для покупателя, и отдельно утверждает альтернативы. Publish создаёт неизменяемую ревизию. Новая ревизия сосуществует со старой, пока старая явно доступна. D1 делает preflight через чтение scenario и catalog, окончательное решение принимает publish на сервере.

## Подбор и сроки

1. В запросе каждый из шести слотов присутствует ровно один раз. При нормализации сервер упорядочивает их канонически. Четыре обязательных — обычная тарелка, стакан, приборы, салфетка. Десертная тарелка по умолчанию выключена, скатерть включена. Гостей 1–12, бюджет 50 000–5 000 000 копеек, заявленное владение 0–99 единиц на слот.
2. Для каждого активного слота считаем `missing = required - min(owned, required)`. Потребность равна числу гостей, для скатерти — одной штуке. На слот покупается один SKU и минимальное целое число упаковок `ceil(missing / pack_units)`. Стоимость строки — цена упаковки, умноженная на число упаковок. При нулевой потребности во всех слотах результат `NO_PURCHASE_REQUIRED`, стоимость нулевая, коммерческие ресурсы отсутствуют.
3. `EXACT_ONLY` пропускает только primary, `APPROVED_ALTERNATIVES` добавляет подтверждённые продавцом варианты. Жёсткие проверки включают активность, остаток, цвет, срок и геометрию. Для покупаемой скатерти допустим свес 15–30 см на каждой стороне, при двух допустимых ориентациях выбирается `NORMAL`. Мягкий цвет входит в цель. Стоимость доставки учитывается один раз.
4. Snapshot читается в короткой транзакции `REPEATABLE READ`. Уже истёкшие резервы исключаются из расчётного удержания, даже если worker ещё не обновил их статус. CP-SAT выполняется вне транзакции и процесса API. Цели фиксируются последовательно: число замен → мягкие цветовые несовпадения → лишние единицы → итоговая цена → ASCII-кортеж SKU. Только `OPTIMAL` на каждой фазе и успешный независимый verifier разрешают сохранить quote.
5. Результаты `QUOTED`, `INFEASIBLE`, `NO_PURCHASE_REQUIRED` возвращаются с HTTP 200. `FEASIBLE` без доказанного optimum и `UNKNOWN` дают 503 `COMPUTATION_LIMIT`. Watchdog всего solve в 5 секунд даёт 503 `COMPUTATION_ABORTED`. CP-SAT использует один поток, seed 42 и 0,2 единицы детерминированного времени на фазу.
6. Бизнес-дата вычисляется в `Europe/Moscow`. При `needed_by` учитываются максимальный срок обработки покупаемых SKU и 0/1 календарный день получения. TTL quote до 900 секунд, резерва до 600 секунд, оба могут закончиться раньше в московскую полночь после последнего возможного дня начала обработки. Равенство `now == expires_at` означает истечение. Смена бизнес-даты между solve и сохранением quote требует нового solve.

Пять хешей имеют разные входы. Бизнес-`request_hash` относится к нормализованным пожеланиям. `snapshot_hash` фиксирует полный шестипольный снимок. `quote_hash` связывает неизменяемые условия с конкретным quote, sandbox и epoch. `solution_hash` сравнивает чистые результаты без служебных UUID и времени хранения. Хеш идемпотентной HTTP-команды использует operationId, метод, канонический путь и проверенное тело без верхнеуровневого `client_run_id`. Все пять используют SHA-256 и зафиксированную JSON-сериализацию.

## Коммерческие транзакции

| Операция | Инвариант |
| --- | --- |
| Quote | Снимок фиксирует состав и цену, а склад не меняется. Перед записью проверяются epoch, business date, статус ревизии, fulfillment version и product versions выбранных SKU. |
| Reserve | Проверяет согласованный hash, срок, актуальность выбранных условий и наличие. Создаёт одно удержание всех строк. Изменение только inventory version оценивается по фактической доступности. |
| Confirm | Использует сохранённый snapshot резерва и accepted hash. Создаёт один `TEST_CONFIRMED`, одновременно уменьшает on-hand и reserved и увеличивает returnable. |
| Cancel reservation / expiry | Освобождает удержанные упаковки один раз. Истёкший резерв нельзя подтвердить даже до прохода worker. |
| Withdrawal | Отзыв SKU или ревизии инвалидирует весь затронутый активный резерв и снимает удержание. Уже подтверждённый заказ можно отменить отдельной командой. |
| Cancel order | Возвращает упаковки в on-hand, уменьшает returnable, сохраняет reservation в `CONFIRMED`. Повторная отмена возвращает текущее состояние без второго возврата. |

Порядок короткой write-транзакции: mutex строки sandbox → часы PostgreSQL после блокировки → обработка истечений → идемпотентность → блокировки SKU в ASCII-порядке → бизнес-мутация, receipt, audit и outbox одним commit. Ожидаемый бизнес-отказ может сохранить законно обработанные истечения и receipt. Неожиданный сбой откатывает транзакцию. Инварианты склада: `0 <= reserved <= on_hand`, `returnable >= 0`, `on_hand + returnable <= 10000`. Worker доставляет outbox с возможными повторными доставками, проекция дедуплицирует их по `event_id`.

При потерянном HTTP-ответе D1 повторяет ту же команду с тем же ключом и после replay перечитывает ресурс. Повтор по исходному epoch сделан специально для точного receipt reset. Обычные запросы старой вкладки получают `SANDBOX_EPOCH_MISMATCH`. В J0 проверяются реальные изменения тестового склада для трёх симуляций: гонка за последний товар, изменение цены и истечение резерва.

## ML и данные для оценки

ML-ветка предлагает кандидатов привязок и черновик формы покупателя. `DISABLED` сохраняет полный ручной путь, `REPLAY` требует точного хеша сохранённого входа, `LOCAL` использует Qwen2.5-VL и OpenCLIP с зафиксированными ревизиями. В режиме LOCAL Qwen извлекает структуру и области изображения, OpenCLIP ранжирует до пяти SKU того же слота и песочницы. Для текста применимы только явно извлечённые поля с evidence и перечнем неясностей. Результат остаётся предложением до подтверждения человеком.

Worker хранит provenance и lifecycle в PostgreSQL. На песочницу допускаются две незавершённые задачи, ожидание в очереди до 60 секунд. Лимит исполнения 120 секунд для анализа контента и 30 секунд для разбора текста. Результат записывается после проверки epoch, состояния и deadline. Поздний callback не меняет terminal state. Хранилище медиа использует внутренние UUID и проверенные image/video форматы. Снимки задания, модель, параметры, хеши и источник результата сохраняются для проверки.

Закрытый benchmark подбора сравнивает жадный baseline, LLM с согласованными инструментами и формальный CP-SAT подход на одинаковых подтверждённых входах. Фиксируются допустимость, точный optimum, ложные отказы, доля задач с известной истиной, время, стоимость и абляции. Для ML нужен отдельный размеченный корпус из 60 сцен и 60 текстов с разбиением 20/40 каждого типа, с provenance и отдельными метриками. Демо-медиа и результаты живой модели в архиве отсутствуют. ## Что подтвердилось при проверке ТЗ

- ZIP читается без ошибок. На временной копии штатный `verify_package.py` прошёл **471 проверку** с Python **3.12.14** и uv **0.13.9**. В том числе 51 golden case, 4 проверки сроков, 7 задач AC/BE, 7 hash vectors, 12 структурных примеров и 47 задач бэклога. Установленный в локальном окружении uv 0.6.14 не находил закреплённую версию Python, повтор выполнен на точной версии инструмента.
- Отдельный `openapi-spec-validator` подтвердил OpenAPI JSON. Схемы OpenAPI и самостоятельной JSON Schema эквивалентны с учётом локальных путей ссылок. CSV-реестр совпадает по путям, operationId, успехам и обязательности ключей. Реестр ошибок совпадает с enum. В DOCX и PDF совпадают 11 глав, набор из 25 ID D2 и набор из 24 сценариев AC-TC.
- **Целевая DDL не применяется как поставлена.** PostgreSQL 17.12 останавливается при создании `guard_product_update`. После исправления только первого выражения останавливается на `guard_inventory_update`. На временной копии заключение каждого `CASE WHEN changed THEN 1 ELSE 0 END` в скобки устранило оба сбоя, после чего создались 25 таблиц и 28 триггеров. Исходные строки сохранены в [database.sql](VK_CaseChamp_TZ_v1/contracts/database.sql#L578) и [inventory guard](VK_CaseChamp_TZ_v1/contracts/database.sql#L597).

## Что сверить на G0

1. Зафиксировать исправление двух SQL-выражений в согласованной версии схемы перед написанием миграций D2-03. Проверку чистой установки PostgreSQL включить в приёмку миграций. Успешная загрузка исправленного DDL пока подтверждает синтаксис и создание объектов.
2. Уточнить wire-семантику `NO_PURCHASE_REQUIRED`. D1 и D2 описывают нормализованные входные данные и нулевые суммы, тогда как `SolveResult` с `quote=null` содержит только `outcome`, `quote`, `reasons`, `minimum_total_minor` и `verification_passed`. Совместимый вариант — оставить OpenAPI как есть и явно описать, что в этой ветке UI показывает количества по отправленной форме, а нулевые суммы следуют из исхода. [Пример ответа](VK_CaseChamp_TZ_v1/contracts/examples/11_no_purchase.json)
3. Уточнить формулировку «commit по hash preview». Согласно OpenAPI и D1, клиент адресует `import_id` и передаёт `expected_catalog_version`. `source_sha256` хранится у preview. При сохранении текущего wire-контракта проверка hash относится к серверной записи preview и сохранённому источнику. [D2, раздел об импорте](VK_CaseChamp_TZ_v1/docs/D2_backend.md#42-импорт) · [D1, экран S1](VK_CaseChamp_TZ_v1/docs/D1_frontend.md#s1-импорт-каталога)

## Запуск реализованного backend

Python-сервис, Alembic и worker находятся в этой папке. Сведения о проверке реализации и ограничения описаны в [отчёте D2](reports/README.md). Трактовки G0 собраны в [решениях по контракту](docs/contract-decisions.md).

### Compose

Из папки `casechamp_dev` создайте локальные пароли и запустите стек.

```bash
python3 scripts/setup_demo_env.py
docker compose up --build --wait
```

API и Swagger доступны на `http://localhost:8080/api/v1/docs`. Проверка готовности — `/api/v1/health/ready`. Для режима REPLAY создайте окружение с параметром `--replay` или задайте `CASECHAMP_ML_MODE=REPLAY` перед запуском Compose. Для проверки через браузер скопируйте сборку D1 в `apps/web/dist` или укажите `CASECHAMP_WEB_DIST`. Доступ извне настраивается через HTTPS с `compose.https.yaml`, собственным доменом в `CASECHAMP_SITE_ADDRESS`, `CASECHAMP_WEB_ORIGIN=https://...` и `CASECHAMP_APP_MODE=production`.

Образ, API и worker используют один lock-файл. Сервис миграций подключается отдельной ролью. Роль API/worker сохраняет данные и не получает DDL или DELETE. Роль очистки используется только worker. Публичный прокси по умолчанию слушает loopback.

### Локальные команды D2

Для закреплённого uv 0.13.9 можно использовать команды ниже. Он установит Python 3.12.14 при первом запуске. Для локального API укажите `DATABASE_URL` PostgreSQL 17, `MIGRATION_DATABASE_URL` владельца схемы, а затем выполните миграции и запустите API и worker в отдельных процессах.

```bash
uvx --from uv==0.13.9 uv sync --locked
uvx --from uv==0.13.9 uv run --locked alembic upgrade head
uvx --from uv==0.13.9 uv run --locked uvicorn app.main:app
uvx --from uv==0.13.9 uv run --locked python -m app.worker
uvx --from uv==0.13.9 uv run --locked pytest -q
uvx --from uv==0.13.9 uv run --locked python scripts/smoke_http.py --origin http://localhost:8080
```

Pytest автоматически поднимает временный экземпляр на UNIX-сокете при наличии PostgreSQL 17 и локального пользователя с правом запуска `initdb`. Переменная `CASECHAMP_PG_BIN` указывает путь к бинарным файлам. Для уже подготовленной отдельной тестовой базы укажите `TEST_DATABASE_URL`. Пользовательскую PostgreSQL-базу тестам передавать нельзя.

### Воспроизведение оценки

```bash
uvx --from uv==0.13.9 uv run --locked python -m app.benchmark --ollama-url http://127.0.0.1:11434
uvx --from uv==0.13.9 uv run --locked python scripts/measure_http.py --origin http://localhost:8080
```

Для B1 нужна локальная модель Ollama `qwen2.5:0.5b`. Без `--ollama-url` отчёт явно помечает B1 как `PROVIDER_UNAVAILABLE`. Готовые значения, версия модели и результаты каждой задачи находятся в `reports/benchmark.json`. Для замера API в лимитах 4 vCPU и 8 GiB запустите Compose с файлами `compose.yaml` и `compose.performance.yaml`.

`LOCAL` устанавливается дополнительной группой `uv sync --locked --extra ml`. Команда `python scripts/prepare_local_model.py` загружает закреплённые публичные ревизии. При ручной установке разместите Qwen в `MODEL_ROOT/qwen/`, веса OpenCLIP в `MODEL_ROOT/clip/model.safetensors` и подготовьте `MODEL_ROOT/model-manifest.json` с полными ревизиями и SHA-256 каждого файла. Для проверки REPLAY на другой бизнес-дате выполните `python scripts/prepare_replay.py YYYY-MM-DD` до пересборки образа. Режим REPLAY и LOCAL имеют одинаковый wire-контракт, происхождение результата различается.
